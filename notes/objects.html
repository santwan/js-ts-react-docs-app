01 — What Objects Are

The Fundamental Data Structure of JavaScript

In JavaScript, an object is a collection of key–value pairs. Each pair is called a property. The key is a string (or a Symbol), and the value can be anything — a number, string, boolean, another object, an array, or a function.

Objects exist because related data belongs together. Instead of five separate variables for a user's name, age, email, city, and active status, you group them in one object. That grouping also enables you to pass all five pieces of data to a function in a single argument, return them together, and store them as one unit.

Every object in JavaScript is a reference type. This means when you assign an object to a variable, the variable does not contain the object's data directly — it holds a memory address (a reference) pointing to where the data lives in memory. This has a critical consequence: two variables can point to the same object, and changing the object through one variable is visible through the other. This was introduced in Topic 01 and applies to every object operation in this topic.

JavaScript
// Object literal — { key: value }
const user = {
  name:   "Arjun",
  age:    25,
  active: true,
};

// No enforcement of shape.
// Any key can be added or
// changed to any type at any time.
user.role = "admin"; // silently allowed
user.age  = "old";   // wrong type — no error
TypeScript
// Define the shape first
interface User {
  name:   string;
  age:    number;
  active: boolean;
}

// Annotate the variable with the interface
const user: User = {
  name:   "Arjun",
  age:    25,
  active: true,
};

user.role = "admin"; // Error: 'role' not in User ✓
user.age  = "old";   // Error: string ≠ number ✓
Why TypeScript requires a shape definition: JavaScript has no mechanism to prevent a wrong type being assigned to a property, or a non-existent property being accessed. Both operations silently produce undefined or wrong values at runtime. TypeScript solves this by requiring you to describe the object's shape — the exact set of properties and their types — in an interface or type alias. Once declared, the compiler validates every property access and assignment against that shape at compile time, before the code runs in a browser or server.

interface vs type — Choosing the Right Syntax

TypeScript provides two constructs for describing object shapes: interface and type. It is important to understand what each one is, how they differ, and when to use each.

An interface is a named contract describing an object's structure. It is designed specifically for this purpose. Interfaces support the extends keyword, which creates a new interface that inherits all properties from an existing one and adds more. Interfaces also support declaration merging — if you declare the same interface name twice in the same scope, TypeScript merges both declarations. This is used when extending third-party library types.

A type alias gives a name to any type expression — not just object shapes. Type aliases can represent union types, intersection types, mapped types, conditional types, and other constructs that interfaces cannot express. However, a type alias cannot be reopened and merged after its initial declaration.

Practical rule: Use interface when defining the shape of an object or class — especially one that may be extended. Use type for union types, intersection types, and cases where you need to express something an interface cannot.

// interface — appropriate for named object shapes
interface Product {
  id:    number;
  title: string;
  price: number;
}

// type alias — required for union types; interface cannot express these
type ID     = string | number;
type Status = "active" | "inactive" | "banned";

// For a plain object shape, both are functionally equivalent
interface PointA { x: number; y: number }
type      PointB = { x: number; y: number }
// PointA and PointB are structurally identical — interchangeable here
02 — Accessing Properties

Dot Notation, Bracket Notation, and Optional Chaining

There are two fundamental ways to read a property from an object, and one safe-access shorthand.

Dot notation (obj.key) is the standard form. It is concise and is used whenever the property name is a known literal identifier written at the time you author the code.

Bracket notation (obj["key"] or obj[variable]) is required in two situations: when the key is stored in a variable and not known at write time, or when the key contains characters that are not legal in an identifier (e.g. a hyphen or space). In all other cases, prefer dot notation.

In TypeScript, using bracket notation with a variable introduces a problem: if the variable is typed as string, TypeScript does not know whether it holds a valid property name of the object. To resolve this, TypeScript provides the keyof operator, which takes a type and produces the union of all its known property names. Typing the key variable as keyof T tells TypeScript that the variable can only hold a valid key of that type — restoring type safety for the bracket access.

interface User { id: number; name: string; age: number }
const user: User = { id: 1, name: "Arjun", age: 25 };

// Dot notation — preferred for known literal keys
console.log(user.name); // "Arjun"
console.log(user.age);  // 25

// keyof User produces the union: "id" | "name" | "age"
// Typing the key as keyof User means only valid property names are allowed
const field: keyof User = "name";
console.log(user[field]); // "Arjun" — TypeScript accepts this ✓

// Without keyof, TypeScript cannot determine which property is being accessed
const key: string = "name";
console.log(user[key]); // Error: Element implicitly has 'any' type
                          // 'string' is too wide — could be any string, not just a valid key

// Accessing a property not declared on the interface
console.log(user.email); // Error: 'email' does not exist on type 'User'

Optional chaining (?.) is a third form of property access used when an intermediate value in a chain may be null or undefined. Without it, accessing a property on undefined throws a TypeError at runtime. With ?., if the left side is null or undefined, the entire expression short-circuits and returns undefined without throwing.

interface User {
  name: string;
  address?: {          // optional property — may not exist
    city:    string;
    pincode: string;
  };
}

const user: User = { name: "Arjun" }; // no address provided

// Without optional chaining: runtime TypeError crashes the program
console.log(user.address.city);   // TypeError: Cannot read property 'city' of undefined

// With optional chaining: returns undefined safely, program continues
console.log(user.address?.city);  // undefined — no crash

// TypeScript enforces optional chaining when the type is optional
// If you try user.address.city without ?., TypeScript will error because
// address could be undefined — it forces you to handle the possibility

// Nullish coalescing (??) provides a default when the result is null or undefined
const city = user.address?.city ?? "Unknown";
// city: string — either the actual city, or "Unknown" as a fallback
03 — Optional and Readonly Properties

Controlling Which Properties Must Be Present and Which Can Change

Real-world objects are rarely uniform — not every property is always present, and some properties should never change after the object is created. TypeScript provides two property modifiers to encode these constraints directly in the type.

The ? modifier marks a property as optional. This has two effects: first, the property can be omitted entirely when creating an object of that type. Second, inside the type, the property's type is widened to include undefined — so if you declare email?: string, TypeScript treats the type of email as string | undefined everywhere it is used. This forces you to handle the case where the property is absent, which prevents a whole class of runtime errors.

The readonly modifier marks a property as immutable after creation. The property must be provided when the object is created, but TypeScript will reject any subsequent assignment to it. This is appropriate for properties that should never change — such as a database-assigned identifier or a configuration constant.

interface User {
  readonly id:   number;    // required AND immutable after creation
  name:          string;    // required AND mutable
  email?:        string;    // optional — type is string | undefined
  age?:          number;    // optional — type is number | undefined
}

// Valid — id and name provided; email and age omitted (they are optional)
const user: User = { id: 1, name: "Arjun" };

// Attempting to reassign readonly — TypeScript rejects this at compile time
user.id   = 99;      // Error: Cannot assign to 'id' — it is a read-only property
user.name = "Rahul"; // ✓ — name has no readonly modifier

// Accessing an optional property without a null check
// TypeScript knows email is string | undefined and requires you to handle it
user.email.toUpperCase();   // Error: 'email' is possibly undefined

// Correct approach 1: optional chaining
user.email?.toUpperCase(); // ✓ — returns undefined if email is absent

// Correct approach 2: provide a fallback with nullish coalescing
const displayEmail = user.email ?? "not provided";
// displayEmail: string — the ?? eliminates undefined from the type

// Correct approach 3: if-check (type narrowing — covered in Topic 02)
if (user.email) {
  user.email.toUpperCase(); // ✓ — inside this block, email is string (not undefined)
}
readonly is a compile-time constraint only. At runtime, the compiled JavaScript has no enforcement — the property behaves like a regular writable property. TypeScript's readonly check exists only in the compiler. If you need true runtime immutability that cannot be bypassed, use Object.freeze(obj), which prevents property mutation at runtime. Note that Object.freeze is also shallow — nested objects are not frozen.
04 — Destructuring

Extracting Properties Into Separate Variables

Destructuring is a syntax that extracts one or more properties from an object and assigns them to individual named variables in a single statement. Without it, accessing multiple properties requires a separate statement per property — which is repetitive when you need to use many properties from the same object.

The destructuring syntax is written on the left side of an assignment using curly braces: const { name, age } = user. This creates two variables, name and age, initialised with the values of the corresponding properties from user.

In TypeScript, each destructured variable automatically inherits the type of the corresponding property from the interface. No additional annotation is needed. TypeScript continues to enforce type safety on every extracted variable throughout its scope.

interface User {
  id:     number;
  name:   string;
  age:    number;
  email?: string;
}

const user: User = { id: 1, name: "Arjun", age: 25 };

// Without destructuring — each property access is a separate statement
const n = user.name; // string
const a = user.age;  // number

// With destructuring — both extracted in one statement
// TypeScript infers: name is string, age is number — from the User interface
const { name, age } = user;

// Renaming: { originalPropertyName: newVariableName }
// Useful when a name conflicts with an existing variable in the same scope
const { name: userName, age: userAge } = user;
// userName: string — holds the value of user.name
// userAge: number  — holds the value of user.age
// The variables 'name' and 'age' do NOT exist — only userName and userAge do

// Default values for optional properties
// When 'email' is absent (undefined), the variable receives the default value
// The default eliminates 'undefined' from the variable's type
const { email = "not-set@example.com" } = user;
// email: string — never undefined, because the default is provided

// Destructuring nested objects
// The syntax mirrors the object's structure
const config = {
  server: { host: "localhost", port: 3000 },
  db:     { host: "db.server",  port: 5432 },
};

const { server: { host: serverHost, port: serverPort } } = config;
// serverHost: string = "localhost"
// serverPort: number = 3000
// Important: 'server' is NOT created as a variable here — only its contents are

Destructuring in function parameters is one of the most common patterns in TypeScript and React. Instead of accepting a full object as a parameter and then accessing properties with dot notation inside the function body, you destructure the needed properties directly in the parameter list. The TypeScript type annotation is placed on the destructured parameter as a whole.

// Approach 1: receive the whole object, access properties inside
function greet(user: User): string {
  return `Hello ${user.name}, you are ${user.age} years old`;
}

// Approach 2: destructure in the parameter list directly
// Behaviour is identical — this is more concise when only a few properties are needed
function greet({ name, age }: User): string {
  return `Hello ${name}, you are ${age} years old`;
}

// In React — every component uses this pattern for props
interface ButtonProps {
  label:    string;
  disabled?: boolean;
  onClick:  () => void;
}

function Button({ label, disabled = false, onClick }: ButtonProps) {
  // label: string, disabled: boolean (default false), onClick: () => void
  // All types inferred from ButtonProps — no extra annotations needed
}
05 — Spread and Rest

Copying, Merging, and Collecting Properties

The spread operator (...), when used inside an object literal, copies all own enumerable properties from a source object into the new object being created. The source object is not modified — the spread always produces a new object.

This is the foundation of immutable updates, which is a required pattern in React. The principle is: instead of modifying an existing object directly (mutation), you create a new object that copies all properties from the original but overrides the ones that changed. You spread the original first, then list the changed properties after. Because object literals are evaluated left to right, any property specified after the spread takes precedence over the corresponding copied property.

The rest syntax performs the inverse operation inside a destructuring expression. It collects all properties that were not explicitly named in the destructuring into a new object. This is commonly used to separate one or two specific properties from the rest of an object — for example, removing a sensitive field before sending data to a client.

interface User { id: number; name: string; age: number }
const user: User = { id: 1, name: "Arjun", age: 25 };

// ── Spread ──────────────────────────────────────────────────────────

// Shallow copy — all properties of user are copied into a new object
// 'copy' and 'user' are now two distinct objects in memory
const copy: User = { ...user };

// Immutable update — copy everything from user, then override 'age'
// The spread copies id, name, and age from user
// 'age: 26' then replaces the copied age value
const updated: User = { ...user, age: 26 };
// updated → { id: 1, name: "Arjun", age: 26 }
// user    → { id: 1, name: "Arjun", age: 25 }  ← original is unchanged

// Merging two objects
// When both objects have the same key, the later one (overrides) wins
const defaults  = { theme: "light", lang: "en", debug: false };
const overrides = { theme: "dark" };
const config    = { ...defaults, ...overrides };
// { theme: "dark", lang: "en", debug: false }
// theme from overrides replaced theme from defaults
// lang and debug from defaults are preserved unchanged

// ── Rest ────────────────────────────────────────────────────────────

// Named properties are extracted; everything else is collected into 'rest'
const { id, ...rest } = user;
// id:   number              — the explicitly named property
// rest: { name: string; age: number } — all other properties collected

// Practical use: strip a sensitive field before sending data to a client
interface FullUser { id: number; name: string; password: string }
const fullUser: FullUser = { id: 1, name: "Arjun", password: "hashed" };
const { password, ...safeUser } = fullUser;
// safeUser: { id: number; name: string } — password is excluded
// Sending safeUser to the client is safe; password is not included
⚡

Spread performs a shallow copy, not a deep copy. When a property's value is itself an object or array, spread copies the reference to that value, not a new copy of it. After spreading, both the original and the copy point to the same nested object in memory. Modifying the nested object through either reference affects both. To update a nested property immutably, you must spread each level individually: {"{ ...user, address: { ...user.address, city: \"Mumbai\" } }"}.

06 — Computed Keys and Index Signatures

Working With Objects Whose Keys Are Not Known at Write Time

In most cases, you know the property names of an object when you write the code — you type them as string literals. However, some objects have keys that are determined at runtime: a collection of scores keyed by subject name, a lookup table keyed by a dynamic identifier, or a configuration object built from user input.

JavaScript supports this through computed property names. When creating an object literal, wrapping a key in square brackets tells JavaScript to evaluate the expression inside the brackets and use its result as the property name. For example, { [variable]: value } creates a property whose name is the current value of variable.

For TypeScript to type objects with dynamic keys, it uses two mechanisms. An index signature is placed inside an interface and describes the pattern for all dynamic properties: [keyName: keyType]: valueType. This means "any property whose key is of keyType will have a value of valueType." The alternative is the Record<K, V> utility type, which expresses the same constraint more concisely and is the preferred form in most cases.

JavaScript — computed keys
const subject = "maths";
const prefix  = "score";

const obj = {
  [subject]:        95,  // { maths: 95 }
  [prefix + "_1"]: 88,  // { score_1: 88 }
};
TypeScript — index signature
// [paramName: keyType]: valueType
interface Scores {
  [subject: string]: number;
}
// any string key → number value

const s: Scores = {};
s.maths   = 95;   // ✓
s.english = "A"; // Error: string ≠ number
// Record<K, V> — the preferred alternative to raw index signatures
// Record<string, number> is semantically identical to { [key: string]: number }
// but reads more clearly and composes better with other utility types
const scores: Record<string, number> = { maths: 95, science: 88 };

// Using a union type as the key — enforces that ALL keys in the union are present
// This turns the object into an exhaustive lookup table
type Status = "active" | "inactive" | "banned";

const statusLabels: Record<Status, string> = {
  active:   "Active user",
  inactive: "Inactive user",
  banned:   "Banned user",
};
// If any of the three keys were absent, TypeScript would report an error
// Adding a new status to the union later forces you to add the label — compile-time safety
Why Record with a union key is powerful: When you type a lookup table as Record<Status, string>, TypeScript verifies that every value in the Status union is present as a key. If you later add a new status to the union and forget to add a corresponding entry in the lookup table, the compiler reports an error. This is called exhaustive coverage — the type system becomes a checklist that prevents oversights when extending the codebase.
07 — Object Utility Methods

Object.keys, Object.values, Object.entries, Object.assign, Object.freeze

JavaScript's global Object provides static methods for inspecting and manipulating objects. These operate on an object's own enumerable properties — properties that belong directly to the object, not inherited from its prototype chain, and that are not marked as non-enumerable.

Object.keys(obj) returns an array of the property names as strings. Object.values(obj) returns an array of the property values. Object.entries(obj) returns an array of [key, value] pairs. Of the three, Object.entries is most commonly used in practice because it provides both key and value together, enabling the most flexible iteration.

interface User { id: number; name: string; age: number }
const user: User = { id: 1, name: "Arjun", age: 25 };

// Object.keys — returns an array of property name strings
const keys: string[] = Object.keys(user);
// ["id", "name", "age"]

// Object.values — returns an array of the property values
const values = Object.values(user);
// [1, "Arjun", 25]

// Object.entries — returns an array of [key, value] pairs
// Each element is a two-element tuple: [string, value]
const entries = Object.entries(user);
// [["id", 1], ["name", "Arjun"], ["age", 25]]

// Typical usage: iterate over all properties using entries
// Destructure each [key, value] pair directly in the forEach callback
Object.entries(user).forEach(([key, value]) => {
  console.log(`${key}: ${value}`);
});
// Output:
// id: 1
// name: Arjun
// age: 25

// Object.assign(target, ...sources)
// Copies properties from source objects into the target object — mutates the target
// In modern code, prefer spread syntax to avoid mutation
const target = { a: 1 };
Object.assign(target, { b: 2 }, { c: 3 });
// target is now { a: 1, b: 2, c: 3 } — mutated

// Object.freeze(obj)
// Prevents all property additions, deletions, and value changes on the object
// Returns the same object, now frozen — applies at runtime (not just compile time)
const constants = Object.freeze({ PI: 3.14159, MAX_SIZE: 100 });
constants.PI = 3; // silently ignored in non-strict mode; TypeError in strict mode
// Object.freeze is shallow — nested objects inside a frozen object are not frozen
Why Object.keys() returns string[] and not (keyof T)[]: TypeScript uses structural typing, which means a variable typed as User may at runtime hold an object that has additional properties beyond what the User interface declares. If Object.keys() returned (keyof User)[], it would assert that only the declared keys are present — which is not guaranteed. Returning string[] is the accurate representation. If you are certain no extra keys exist on the object, you may cast: (Object.keys(user) as (keyof User)[]) — but this is your assertion, not something TypeScript can verify.
08 — Extending and Intersecting Types

Reusing Type Definitions Without Repetition

In a real application, many object types share a common structure. Every database entity, for instance, typically has an id assigned by the database, a createdAt timestamp set on creation, and an updatedAt timestamp updated on every change. Writing these three fields on every interface would be repetition. If the field name or type ever changed, every interface would need updating.

TypeScript solves this with interface extension. The extends keyword creates a new interface that inherits all the properties of the parent interface and adds its own. The child type is a superset of the parent: every value of the child type is also a valid value of the parent type. You define shared fields once, and all domain-specific interfaces inherit them.

For type aliases, the equivalent is the intersection operator (&). An intersection type has all the properties of both operand types. Use extends with interfaces; use & with type aliases.

// Base interface — properties common to all database-backed entities
interface Entity {
  readonly id:        number;
  readonly createdAt: string;
  updatedAt:          string;
}

// User extends Entity — inherits id, createdAt, updatedAt automatically
interface User extends Entity {
  name:  string;
  email: string;
}
// A User object must have: id, createdAt, updatedAt, name, email

// Product also extends Entity — same base, different domain fields
interface Product extends Entity {
  title: string;
  price: number;
}

// AdminUser extends User — adds role and permissions on top of User's fields
interface AdminUser extends User {
  role:        "admin";      // literal type — only the string "admin" is valid here
  permissions: string[];
}

// Intersection with type aliases
type Timestamps = { createdAt: string; updatedAt: string };
type UserBase   = { name: string; email: string };
type UserWithTs = UserBase & Timestamps;
// { name: string; email: string; createdAt: string; updatedAt: string }

// Generic base interface — used to type all API responses consistently
// T is a type parameter — replaced with a concrete type at each usage site
interface ApiResponse<T> {
  data:    T;
  status:  number;
  message: string;
}

// Usage — TypeScript substitutes T with the provided type
type UserResponse    = ApiResponse<User>;      // { data: User, status, message }
type UsersResponse   = ApiResponse<User[]>;    // { data: User[], status, message }
type ProductResponse = ApiResponse<Product>;  // { data: Product, status, message }
09 — Utility Types for Objects

Transforming Existing Types Without Repeating Their Definitions

TypeScript ships with a set of built-in utility types — generic types that accept an existing type and produce a modified version of it. They exist to eliminate duplication. Instead of writing a new interface from scratch when you need a slightly different version of one you already have, you derive the new type from the existing one. When the source type changes, all derived types update automatically.

The five utility types most relevant to objects are: Partial, Required, Readonly, Pick, and Omit. Each one takes an existing type as input — denoted T — and produces a transformed version of it.

interface User {
  id:    number;
  name:  string;
  email: string;
  age:   number;
}

// Partial<T> — makes every property optional
// Used for PATCH endpoints where the client sends only the changed fields
type UserPatch = Partial<User>;
// { id?: number; name?: string; email?: string; age?: number }

function updateUser(id: number, changes: UserPatch): void { /* ... */ }
updateUser(1, { name: "Raj" });          // ✓ only name provided — rest are optional

// Required<T> — makes every property required (reverses optional)
// Used when you know all fields have been validated and are present
type CompleteUser = Required<User>;
// { id: number; name: string; email: string; age: number } — no optionals

// Readonly<T> — makes every property readonly
// Used to protect data from being mutated inside a function
function displayUser(user: Readonly<User>): void {
  user.name = "X"; // Error: cannot assign to 'name' — it is readonly here
}

// Pick<T, K> — keep only the properties named in K, discard the rest
// Used for summary/preview shapes that show a subset of the full data
type UserPreview = Pick<User, "id" | "name">;
// { id: number; name: string }

// Omit<T, K> — remove the properties named in K, keep the rest
// Used for create DTOs — the database assigns 'id', so it should not be in the input
type CreateUserDto = Omit<User, "id">;
// { name: string; email: string; age: number }

// Combining utility types — Update DTO: id is required, everything else optional
// Step 1: Pick<User, "id"> produces { id: number } — id is required
// Step 2: Omit<User, "id"> produces { name, email, age } — User without id
// Step 3: Partial wraps that result, making all three optional
// Step 4: & intersects both parts into one type
type UpdateUserDto = Pick<User, "id"> & Partial<Omit<User, "id">>;
// { id: number; name?: string; email?: string; age?: number }
10 — Structural Typing

Compatibility Is Determined by Shape, Not by Name

TypeScript uses a type system called structural typing. Understanding this principle is essential because it affects how type compatibility works throughout the entire language.

In a nominally typed language such as Java, two types are compatible only when an explicit relationship exists between them — one class must extend another, or implement its interface. The type's name or declared lineage is what determines compatibility.

TypeScript works differently. Two types are compatible if they have the same structure — the same set of properties with compatible types. A function that expects a parameter of type {"{ name: string }"} will accept any object that has a name property of type string, regardless of what interface that object was declared with, and regardless of whether it has additional properties.

This is also why TypeScript is described as using duck typing at the type level — if an object has the properties required by a type, it satisfies that type, with no explicit declaration of the relationship needed.

interface Named { name: string }

// This function requires an argument that has at least a 'name: string' property
function printName(obj: Named): void {
  console.log(obj.name);
}

// A plain object literal with exactly the required shape
printName({ name: "Arjun" }); // ✓

// An object with additional properties beyond what Named requires
// Extra properties do not break structural compatibility
const user = { name: "Arjun", age: 25, active: true };
printName(user); // ✓ — 'user' has 'name', so it satisfies Named

// A completely different interface — still compatible because the shape matches
// Product was never declared to implement or extend Named — but it has 'name: string'
interface Product { name: string; price: number }
const product: Product = { name: "Keyboard", price: 1500 };
printName(product); // ✓ — Product has 'name: string', so it satisfies Named

// An object that does not have the required property
printName({ id: 1 }); // Error: Property 'name' is missing in type '{ id: number }'
Practical implication of structural typing: You do not need to explicitly declare relationships between types in TypeScript. If a third-party library returns an object that has a name property, and your code accepts anything with a name property, they are automatically compatible — no imports, no casting, no explicit declarations required. This makes TypeScript significantly less verbose than nominally-typed languages while still providing the same level of type safety.
11 — Interview Q&A
Interview JavaScript + TypeScript — answer these out loud
What is the difference between dot notation and bracket notation for property access?
Dot notation (obj.key) is the standard form, used when the property name is known as a literal identifier at write time. Bracket notation (obj[variable]) is required when the key is stored in a variable and is not known until runtime, or when the key contains characters that are not valid identifiers. In TypeScript, the dynamic key variable should be typed as keyof T when using bracket notation — this tells the compiler that the variable can only hold a valid property name of that type, preserving type safety on the accessed value.
What is the difference between interface and type in TypeScript?
Both can describe object shapes and for that purpose are largely interchangeable. Key differences: interface supports the extends keyword for inheritance and supports declaration merging — declaring the same name twice causes TypeScript to merge both declarations. type alias is more flexible — it can represent union types, intersection types, mapped types, and conditional types, which interfaces cannot. For plain object shapes that may be extended, use interface. For unions and complex type expressions, use type.
What is the difference between optional (?) and readonly in a TypeScript interface?
Optional (?) affects whether a property must be present when the object is created. An optional property may be omitted entirely — its type becomes T | undefined inside the type, and TypeScript requires you to handle that possibility before using the value. readonly affects mutability, not presence — the property must be provided when the object is created, but TypeScript rejects any assignment to it after creation. readonly is a compile-time constraint only; the underlying JavaScript object remains mutable at runtime.
What does the spread operator do with objects and what is its shallow copy limitation?
The spread operator copies all own enumerable properties from a source object into a new object literal. It is the standard mechanism for immutable updates: {"{ ...original, key: newValue }"} produces a new object with all original properties, overriding the specified one. The shallow copy limitation means that only the top-level properties are copied — if a property's value is an object or array, the spread copies the reference to that value, not a new copy of it. Both the original and the new object then point to the same nested object in memory, meaning mutations to the nested object are visible through both references.
What are Partial, Pick, and Omit? Give a practical use case for each.
Partial<T> makes all properties optional — used for PATCH request bodies where only changed fields are sent. Pick<T, K> produces a type with only the specified properties — used for summary shapes where exposing the full object is unnecessary or too large. Omit<T, K> produces a type with the specified properties removed — used for create request bodies where the server assigns id, so the input type should not include it, or to strip sensitive fields before sending data to a client.
What is structural typing and how does it differ from nominal typing?
Structural typing means compatibility is determined by the structure of a type — the set of properties and their types — rather than by the type's declared name or explicit inheritance relationships. In TypeScript, any object that has at least the required properties satisfies a type, regardless of what interface it was declared with. Nominal typing, used in Java and C#, requires an explicit declared relationship — a class must explicitly extend another class or implement an interface to be compatible with it. TypeScript's structural approach reduces boilerplate while maintaining the same level of safety.
Why does Object.keys() return string[] and not (keyof T)[] in TypeScript?
Because TypeScript uses structural typing, a variable typed as User may at runtime hold an object with additional properties beyond what the User interface declares. Returning (keyof User)[] would assert that only the declared keys exist, which is not guaranteed. Returning string[] is accurate because the actual keys at runtime may include undeclared extras. If you are certain no extra keys exist and need typed keys, you can cast: (Object.keys(user) as (keyof User)[]) — but this is your assertion, not a TypeScript guarantee.
12 — Key Takeaways

JavaScript + TypeScript — What to Lock In

  • An object is a collection of key–value pairs. In TypeScript, always define its shape with an interface or type alias before use — this is what allows the compiler to validate every property access and assignment.
  • Use interface for named object shapes that may be extended. Use type for union types, intersection types, and complex expressions that interfaces cannot represent.
  • Dot notation for known keys. Bracket notation for dynamic keys — type the key variable as keyof T to maintain type safety on the result.
  • Optional (?) makes a property absent-able. Its type becomes T | undefined — you must handle that before using the value. readonly prevents reassignment after creation — compile-time only.
  • Use optional chaining (?.) to safely navigate chains where a value may be absent. Use nullish coalescing (??) to provide a fallback default value.
  • Destructuring extracts properties into variables in one statement. TypeScript infers each variable's type automatically from the source type. Provide defaults for optional properties to eliminate undefined from the extracted variable's type.
  • Spread copies properties into a new object — the standard immutable update mechanism. It is shallow: nested objects remain shared between original and copy. Spread each nested level individually for deep updates.
  • Rest collects all non-destructured properties into a new object. Used to separate or strip specific fields such as sensitive data.
  • Record<K, V> types dynamic-key objects. Using a union type as K enforces that all values in the union are present as keys — exhaustive coverage guaranteed at compile time.
  • Use the utility type combination Pick<T, "id"> & Partial<Omit<T, "id">> for update DTOs. Define the entity once; derive all request/response shapes from it to eliminate duplication.
  • TypeScript uses structural typing — two types are compatible if they share the same structure, regardless of name or declared relationship. Any object with the required properties satisfies a type.
  • Object.keys() returns string[], not (keyof T)[] — cast explicitly only when you are certain no undeclared properties exist on the object at runtime.
